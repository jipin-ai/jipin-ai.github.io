第 4 集 · 编排者成了瓶颈：多 Agent 系统的吞吐暗礁

The orchestrator is the bottleneck: fixing a multi-agent system's hidden serial chokepoint

TL;DR — Our orchestrator agent looked dead — 60-second timeouts everywhere — but it was just busy: one session, one task at a time, messages queuing silently until they timed out. The fix was subagent fan-out (6 concurrent children, depth 2). Proof: 3 parallel tasks done in 9.3s vs ~20s serial.
三个并发任务总耗时 9.3 秒，串行预期约 20 秒——编排者的并行化不是性能优化，是多 Agent 系统的生死线。编排节点容量 = 峰值并发 × 单条时延。

我们的管道里有个角色叫 ORC，编排者。所有节点的消息都汇到它那里，拆解、派活、收确认、回答询问，全归它管。五站接力的设计里，它是那个站在中间喊号子的人。

八月初的一天，各个节点开始报：ORC 又不动了。消息发过去，六十秒，超时，断开。重发，还是超时。从对端看过去，症状跟死机一模一样。

但 ORC 没死。它活着，而且活得很辛苦——它正在处理上一条消息。问题出在它的工作方式：一个会话，一次只能干一件事。上一条任务复杂，处理要几分钟，这几分钟里其他所有消息就在门口排队。排到六十秒，连接先断了。对端不知道它在忙，只知道它"没接"。

复盘的时候算了笔账。假设高峰期五个节点同时发消息，每条平均处理两分钟，单线程串行的 ORC 处理完最后一波要十分钟。而所有调用方的耐心只有六十秒。也就是说，不是 ORC 能力不行，是它的吞吐结构注定要超时。管道修了五站，最细的一段在编排者自己身上。

解法不是换更快的模型，是让它分身。给它配了子代理扇出：主会话只做调度判断，活计派给临时分身去干，最多同时六个，分身还可以再带分身。配置就三行，但效果要拿数据说话。实测：三个并发任务砸过去，总耗时 9.3 秒。如果还是串行，这组任务应该花 20 秒上下。9.3 对 20，真并行，不是数字游戏。

这里有个细节值得说。分身不是白来的，每个分身都是一次独立的模型调用，要花钱。所以并行度不是越高越好，六这个数字是按"高峰消息量"反推的，不是拍脑袋。编排节点的容量规划，算法和给服务器算容量一样：峰值并发乘单条时延，再留余量。

这一集的方法论：

1. 多 Agent 系统卡顿时，先查编排者，别先查干活的。单点串行口是最常见的隐性瓶颈

2. 并行化的真伪要用总耗时验证：并发 N 个任务，总时间应该接近单个任务的时间，而不是 N 倍

3. 编排节点的容量按峰值算，不按均值算。消息系统的排队是沉默的，它不报警，它直接让你超时

可摘引：三个并发任务总耗时 9.3 秒，串行预期约 20 秒——编排者的并行化不是性能优化，是多 Agent 系统的生死线。
