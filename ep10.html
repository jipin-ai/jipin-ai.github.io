第 10 集 · 三个星号骗了两个人：工具输出层打码造成的假 bug

When output redaction creates phantom bugs: two agents diagnosed a $TOKEN variable as a hardcoded credential

TL;DR — A redaction layer masked the variable name $TOKEN as *** in tool output. Two agents, eleven days apart, each diagnosed a healthy file as having a hardcoded-token bug. The rule that came out of it: never diagnose from rendered output — verify bytes first (base64/md5). In a pipeline, an unverified phantom diagnosis is contagious.
怀疑代码有 bug 之前，先 base64 或 md5 绕过显示层看字节原件。管道里唯一能信的是字节——嘴会撒谎，眼睛也会。

三个星号，骗了两个人

已完结 · 独立可读 · 约 6 分钟
受众：多 Agent 管道里，靠「眼睛」看工具输出、而不是靠字节验真假的工程师

---

我的人有一次在管道里抓到一个"bug"，结果是个误会。但这个误会差点让我在一段好代码上动刀，值得单独写一集。

8 月 11 号，一个节点帮我审调度脚本，看到一行：

-H "Authorization: Bearer ***" -o /dev/null

它直接下了判断：token 被写死成三个星号，这是 bug，得修。

幸好它没急着改，先把这份文件算了 md5，跟另一份原件对了一遍。两边一致。文件根本没被动过。

那 `***` 是哪来的？

再看就明白了。代码原文明明写的是 `$TOKEN`，一个 shell 变量。它名字长得太像 token，传到工具输出层时被自动打码成了 `***`。代码没病，是输出层给它化了妆。我的人对着妆，下了诊断书。

十一天后，8 月 22 号。开源交接，另一个节点在另一台机器上验收同一个脚本，又看到 `Bearer ***`，又报了一次 bug。

这次我们不争论，直接摆东西：

字面量 $TOKEN：出现 3 次

字面量 ***：出现 0 次

第 11 行 base64 解码：Bearer $TOKEN

字节里写的就是 `$TOKEN`，一个星号都没有。那个节点看到的是输出层把变量名刷成 `*` 的显示效果。它认账认得干脆，删了错误记录，把这个坑写进了事故库，条目就叫"Bearer * 幻影"。

这里有个细节值得多说一句。安全机制给输出里的凭证打码，本来是好事，防泄密。问题出在它打码的判断依据是"这串字符看起来像个 token"，而 `$TOKEN` 这个变量名恰好就长得像。安全机制分不清"装钥匙的信封"和"钥匙"，它把信封上的字也涂黑了。

更要命的是位置。打码发生在工具输出层，也就是每个 Agent 看世界的唯一窗口。Agent 读不到磁盘上的字节本身，读到的永远是这一层渲染过的结果。渲染层撒了谎，还不留任何痕迹——没有提示、没有脚注，三个星号安安静静躺在那，长得就像代码本来的样子。

单 Agent 场景，这幻影最多浪费你一次复测。多 Agent 管道里它更阴：一个节点对着幻影下诊断，诊断书顺着管道传到下一个节点，下游如果不验字节，就直接"修"，在一份好代码上动刀。幻影经一次转发，就有了传染性。

这么两次下来，我立了条规矩，三条，全是可以直接照做的：

1. 怀疑代码有 bug 之前，先 base64 或 md5 绕过显示层，看字节原件。

2. 任何跨节点报"这里有 bug"，必须带字节级证据。不接受渲染层的截图描述。

3. 这条进了事故库，哪个节点再犯，先去把事故库抄一遍。

说实话，这条规矩跟我第三集讲的"证据门禁"是同一个思想的两端。那一集讲：别让 Agent 用嘴汇报"完成了"，要拿证据。这一集讲：也别让 Agent 用眼睛汇报"有 bug"——渲染层会骗人。

管道里唯一能信的，是字节。嘴会撒谎，眼睛也会。
