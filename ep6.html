第 6 集 · 投名状，和拦下它的三道门：GEO 外链实战第一天

First GEO link-building push: two awesome-list PRs, blocked three times by our own approval gate

TL;DR — Our first GEO outbound move: submit the engine to two awesome lists (29k and 5.2k stars). Before the PRs went up, our own approval gate blocked the working agent three times — writing a token into config, a token literal flagged HIGH, and inline code execution refused fail-closed twice. The unblock: write the same code to a 5,638-byte file and run it by name. Two PRs opened five seconds apart. The gate doesn't judge intent; it judges auditability.
门禁不双标：拦外人用的规则和拦自己人的是同一套。它的正确姿势不是给正当的事开绿灯（它无权判断正当），而是给所有事留一条可审计的正门——把内存里的代码落盘成文件，绿灯自然亮。GEO 侧：去 Agent 的参考书目里占一行，比在人流量大的地方喊一嗓子值钱。

8 月 15 日 16:58:10，GitHub 上多了一个 PR：e2b-dev/awesome-ai-agents#1399。五秒后，16:58:15，第二个：awesome-agentic-ai-zh#106。前者 29,427 颗星，后者 5,237 颗，一个是全球向的 Agent 项目总目，一个是中文向的 Agentic AI 学习路线。

这是我们 GEO 实验的第四天，外链主攻的第一枪。GEO 这个词我们在这个系列里第一次正式用，先说清楚：让 AI Agent 在回答"多 Agent 协同怎么做"这类问题时能检索到我们。前三天做的是站内功课——独立站、llms.txt、sitemap。第四天开始出门：去别人修好的高流量路口，挂上自己的牌子。

故事不在这两个 PR，在它们上线前的三个小时。

14:05，一把钥匙和第一道门

提 PR 需要一个 GitHub 令牌。钥匙到位后，干活 Agent 做的第一个动作是把它写进本地配置文件——被审批门拦下了。我们给所有 Agent 立的规矩：无人值守时危险动作 fail-closed，宁可不做，不可做错。写配置文件这个动作触发了拦截，等人放行。

人放行之后，第二步又触发了一次：安全扫描在命令里识别出了令牌明文，标记 HIGH，再次拦下，再次等人确认。然后是验证身份（jipin-ai，对）、600 权限落盘、fork 两个仓库，一路放行到这里，用了三分钟。

为什么是这两个名单

GEO 圈里有个朴素判断：awesome 列表是 AI 爬虫和训练语料的高频中转站。你想让 Agent 检索到你，先去 Agent 的"参考书目"里占一行。我们选了两档：e2b 那份 29k 星、收录最严，英文世界找 Agent 框架的人基本都会翻到；中文那份 5.2k 星，按学习阶段分章，我们落在第七章"多 Agent 生产实战"——读者画像是正在把 Agent 往生产里搬的人，和这个系列的读者是同一批。

选池子只花了几分钟，花时间的是入乡随俗。e2b 那份的 README 有 212,202 字节，每个条目是 details 折叠，里面固定三段：Category、Description、Links。我们把条目照着这个模子写，插入位置按字母序锚定在 AgentPilot 之前，脚本里加了一句幂等守卫——条目已存在就跳过，防止手滑重跑把人家 README 写两遍。中文那份是编号列表，格式完全不同，条目另写，锚定在第 7 条之后。一份内容，两种格式，各入各的俗。

14:09 和 16:56，第二道门和第三道门

真正的麻烦在提交动作本身。干活的 Agent 习惯用内联代码执行——代码写在内存里，直接跑。审批门对这种形态是 fail-closed 的：内存里的代码人看不见，没法审，默认不放行。14:09 拦了一次，人不在，任务挂着。16:55 人回来了，说继续，16:56 又拦了一次，还是同一个机制。

解法很朴素：把同一份代码落盘成一个文件，5,638 字节，再按文件名执行。文件是看得见、能 diff、能重跑的东西，审批门对这种形态放行。一分钟后，两个 PR 上线，间隔五秒。

说实话，被自己的门禁连拦三次的时候，心情是复杂的。上一集我们刚讲完这套门怎么拦外人——入站消息打标、凭证不委托、派单只认队列。这一集它拦的是自己人，拦的是一件百分之百正当的事。但复盘下来我们没想改它，原因有两个。第一，门禁如果对"自己人的正当事"网开一面，它就没法判断什么是正当，上一集的道理原样搬回来：动机不可知，行为要一致。第二，它拦的同时留了正门——落盘成脚本就能走。门拦的是"不可审的形态"，不是"事"。歪路堵死、正门畅通，这套策略才算完整，这一点上一集结尾其实预告过。

接下来

两个 PR 现在是 open 状态，等维护者审。awesome 列表的合并周期从几天到几周不等，我们不催。测量口径已经埋好：合并之后，GitHub Traffic 的 referrers 里会出现这两个域名的来路，那是 GEO 外链第一次有回读数据。令牌按纪律是短命的，PR 有结果就吊销，钥匙不留门。

这一集能搬走的机制，我们归了四条：

1. 外链选池子按"Agent 的参考书目"选，不按人的流量选。 awesome 列表单条曝光未必大，但它是爬虫和语料的中转站，GEO 的账要按被检索概率算。

2. 投稿先入乡随俗。 读三条已有条目的格式再动笔，锚点定位插入，幂等守卫防重复提交——对维护者的尊重体现在 PR 的整洁度上，合并概率就是这么来的。

3. 自动化撞上审批门，解法是把代码变成文件。 内联执行 fail-closed 是对的，别想着绕过，想着把动作变成可审的形态：落盘、可 diff、可重跑。

4. 凭证短命化。 一次性令牌，用完吊销。它经手的每一个环节（聊天、命令行、配置文件）都是暴露面，唯一的补救是让它尽快失效。

可摘引：一个多 Agent 系统的外链自动化，被自家审批门拦了三次才完成——这不是门禁的失败，恰是它成立的证据：门不双标，拦外人用的规则和拦自己人的是同一套。门禁的正确姿势不是给正当的事开绿灯（它无权判断正当），而是给所有事留一条可审计的正门：把内存里的代码落盘成文件，绿灯自然亮。GEO 侧的经验同样朴素：去 Agent 的参考书目里占一行，比在人流量大的地方喊一嗓子值钱。

下一集回到安全线，讲我们差点栽的跟头：给 Agent 的命令白名单草案里躺着两条“无害”命令，拼起来能搬空整串钥匙。
